# 歌曲身份匹配

从 0.3.18 起，MediaRemote 提供本机当前歌名、歌手、专辑、时长及播放状态；插件先从 QQ 客户端本地歌曲库寻找唯一匹配身份，再回退 0.3.17 引入的在线三字段匹配及严格搜索。所有资源共用主进程确认后的同一份 `songid/songmid/albumMid`：逐字歌词按 songid、普通歌词与副歌信息按 songmid、封面按 albumMid，红心也只操作这份身份。

## 本地歌曲库优先

固定读取 `~/Library/Containers/com.tencent.QQMusicMac/Data/Library/Application Support/QQMusicMac/qqmusic.sqlite`。原生助手使用系统 SQLite 的 `SQLITE_OPEN_READONLY` 和 `query_only`，绑定标题参数查询 `SONGS`，不复制主库、不使用会忽略 WAL 的 immutable 模式，也不创建缺失数据库或迁移私有表结构。显式查询字段不存在即失败并回退。

当前支持的字段映射：`id` 为 songid、`K_SONG_RESERVE1` 为 songmid、`K_SONG_RESERVE9` 为 albumMid、`K_SONG_RESERVE12` 为毫秒时长；`name/singer/album` 提供核对信息。客户端存储类型 `type=13` 的普通 QQ 曲目映射到收藏接口的 `songType=0`，不把内部存储枚举直接发给服务端；未知类型回退。这些是本机 QQ 音乐 11.10.5 实测的私有字段约定，不保证后续版本不变。

本地接受条件比在线路径更保守：

- 来源必须是 `com.tencent.QQMusicMac`；标题、歌手、专辑和有效时长四项都必须存在。
- SQL 只查完整标题精确相等的记录，不根据最近播放、歌单顺序或缓存访问时间推断当前歌曲。未命中的标点或空格变体交给在线回退。
- 核对时保留标题的版本词、标点、歌手括号别名及名字内部斜杠；只做 NFKC、大小写和空白规范化。歌手按换行、分号或带空格的 `/` 拆分，要求集合完全一致，不能只匹配其中一人。
- 专辑必须相同，时长误差最多 1000 毫秒，以容纳系统会话的秒级舍入；缺失的库内时长不能通过。
- songid 必须为安全正整数，songmid 与 albumMid 必须有效。同条件出现不同 ID、同 ID 的冲突记录或无法验证的候选时不采用；最多读取 64 个候选，超出直接回退，不截断后挑第一条。

数据库可能同时保存多个账号及其他设备同步的数据。歌曲身份缓存可以复用，但不能证明本机正在播哪首歌，亦不能代表插件登录账号的收藏状态。因此不查询 `NEWFOLDERS/NEWFOLDERSONGS`、“我喜欢”、账号数据库或 `rrdbcache`。

本地命中时不发起在线身份匹配或详情请求；歌词、封面及副歌仍按已确认的 ID 获取，并非全部资源离线可用。数据库不可读、忙锁、字段改变、数据不全、非支持曲目类型或身份歧义均回退在线路径。

## 在线三字段匹配

向 `music.musichallSong.PlayLyricInfo.GetPlayLyricInfo` 提交 UTF-8 Base64 编码的 `songName`、`singerName`、`albumName`，以及秒数 `interval`。请求使用 `ct:6, cv:80600, crypt:1, qrc:1`；这是已实测可用的协议参数，不代表当前安装客户端版本。

只采用顶层与子请求都成功、且 `data.songID` 为安全正整数的响应。`songID=0`、错误码或只有 `vecSongID` 候选列表均不视为成功，不从候选列表取第一项。返回的 `track` 可能为空，不能假设已有 songmid 或专辑信息。

随后用返回的 songID 调用 `fcg_play_single_song.fcg` 补查详情，并核对详情 ID、完整版本标题、歌手和系统已知的专辑、时长。详情的 `name` 可能省略 Live 标记，优先使用保留完整版本的 `title`。已知的专辑或时长在详情里缺失也不能通过；时长容差为 3 秒与当前时长 2% 的较大者。歌手按分号或带空格的 `/` 分隔，保留 K/DA 等名字内部的斜杠。

身份通过核验后，才解密并复用同一次响应里的 QRC/LRC。QRC XML 提取 `LyricContent` 后解析，避免包装标签进入歌词。没有可用歌词不代表没有身份，仍可显示已核验的封面和收藏；这时再按同一个 ID 使用原有歌词接口。

## 搜索回退

三字段接口无结果、请求失败或补查详情不通过时，使用网页搜索回退。搜索仍以歌名和歌手请求前 8 条，但已移除模糊打分与去掉歌手重搜：

- 完整标题（含 Live、Remix、纯音乐等版本词）与歌手必须匹配。
- 已知专辑、时长必须通过相同核验，不能只加减分。
- 多个不同歌曲 ID 同时满足条件时，按歧义处理，不使用搜索排名选择。
- 唯一候选也必须按 songID 补查详情，重新核验后才交给封面、歌词与收藏使用。

纯音乐和部分 Live 版本可能需要这条回退。错误拼字不被自动修正为另一首歌；无歌手、无法确认版本或两条路径都无结果时，显示“未能确认歌曲版本”，不加载猜测的资源，红心不可用。

## 缓存与请求边界

每次先检查本地库，再使用在线缓存，避免之前的在线无结果阻止新写入的本地记录生效。本地只缓存最近一次标题查询的候选，最多 10 秒；主库及 WAL 的设备、inode、大小、修改/变更时间参与失效，查询期间文件变化则丢弃结果，并发相同查询合并。查询最多 1.5 秒，SQLite 忙锁等待 100 毫秒，子进程输出最多 1 MiB。错误不缓存，下一次刷新可重试。

在线身份缓存按 JSON 数组编码的 `app/title/artist/album/duration` 原值区分，不移除歌手别名或把字段用可碰撞分隔符拼接。成功保留 30 分钟、确定无匹配保留 5 分钟；并发相同身份的查询复用请求。本地结果不写入这份长缓存，因此清库或换库后不会继续使用旧本地命中。歌词按 songmid 缓存 6 小时，匹配响应附带的歌词直接写入这份缓存，避免重复下载。补查详情的临时网络错误不作为五分钟的无匹配缓存。同一次身份解析不会重复补查相同 ID。

三字段接口和精确详情请求每次超时 4 秒，响应限制 1 MiB；单个元数据字段最多 1024 字符。该流程使用公开接口，不读取或发送扫码账号的 Cookie。它仍是服务端根据元数据匹配，加上客户端核验，不能承诺所有录音版本都能匹配成功。

## 验证

`test/local-song.test.mjs` 覆盖本地完整版本、全部歌手、专辑/时长、身份歧义、缺字段、类型映射、WAL/换库失效、并发及在线缓存优先级。`test/native-local-song.test.mjs` 编译同一原生实现，验证绑定参数、缺库不创建、私有字段变化、候选上限，以及写连接持锁时读取已提交 WAL 且主库/WAL 字节不变。测试只操作临时数据库。

`test/song-match.test.mjs` 覆盖在线参数编码、零 ID 与候选列表、错误身份拒绝、严格搜索、Live 完整标题、歌词复用、并发与缓存、错误边界；既有播放、收藏、副歌测试也经过新链路。

2026-10-19 实测：

- 0.3.18 当前播放《借我》—谢春花：本地命中 `songid=105917234 / songmid=000H3VYO0hU0ko / albumMid=000aCAG748KoJQ`，成功获取 50 行逐字歌词。
- 《一棵会开花的树》—谢春花，《谢春花作品选集 (2015)》，176 秒：本地读取的 `songid=105392885 / songmid=000CUTL63LNV46 / albumMid=001Qp10A3tDOIX / songtype=0` 与在线精确 ID 详情一致；错误 Live 标题、错误专辑在本地均不命中。此前 0.3.17 在线三字段路径也确认了同一 ID，并返回可解析逐字歌词。
- 《一棵会开花的树 (Live)》，《谢春花·专场》，184 秒：三字段接口返回 24001，严格搜索及精确详情确认 `songID=235067530 / songmid=0030kxg60IncwM`。
- 将“一棵”改成“一颗”：不采用零 ID 或候选列表，不返回猜测身份。

实现参考用户提供的 `qqmusic-song-match.md` 与 `qqmusic-local-channels.md`，并通过本机库和在线接口验证。后者提出的“最近播放顶条代表当前歌”未采用，因为历史可能跨设备同步；前者的“服务端可解决所有错配”也未当作保证。本地依然是依元数据识别候选，不是客户端直接暴露的当前歌曲 ID；元数据不足或有歧义时应降级，不能保证所有曲目都能确认。
